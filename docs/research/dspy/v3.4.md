# DSPy 3.4.0 — what changed, and what upgrading costs this repo

**Part of:** [R009 · DSPy](INDEX.md) · **Released:** 2026-09-25 · **Installed today:** 3.3.1, pinned in
`uv.lock`; `pyproject.toml` asks only for `dspy>=3.2.1` in the `optimizer` extra · **Source:** the
GitHub release notes for tag `3.4.0` and a diff of the two tagged source trees.

## Can we move to 3.4?

**Yes, and the move is prompt-neutral. Measured, not assumed.** DSPy has never run in production (no
image installs it), so no deployed behaviour depends on the version. The one real tie is S246's
golden fixture and the kernel literals copied from it. Both are 3.3.1's exact `ChatAdapter` text, so
the question is whether 3.4 renders or parses that text differently.

*[measured 2026-09-30]* The repo's own generator, `build_golden()` in
`scripts/render_guided_turn_golden.py`, was run in a throwaway environment with `dspy==3.4.0`, and its
output was compared with the committed `tests/fixtures/deliberation_guided_golden.json`. The result:
`prefix`, `requirements`, the 3 `system` cases, the 3 `user` cases and all **17 parse cases** are
**identical**. Nothing but the recorded `dspy_version` string would change.

**What the upgrade takes:** `uv lock --upgrade-package dspy`, then regenerate the golden (a one-line
version-string diff). It needs the full cycle, because the lock file changes, and it is a PATCH. Its
precondition holds: 3.4 needs pydantic ≥ 2.11, and the lock has **2.13.5**.

**What it does not change:** 🪤 `diskcache` is **still a base dependency** of 3.4.0. 3.4 only
postpones *building* the cache until a cache tier is enabled. Installing DSPy in any image still
installs `diskcache`, so DL-184's accepted advisory (*"installed by 0 of 15 Dockerfiles"*) still
keeps DSPy out of production images.

## The changes that matter here

### LM layer: "the transition release; 3.5 is the migration deadline"

- A new built-in engine layer (`dspy.lm15`). `engine="auto"` prefers native execution and falls back
  to LiteLLM *before* inference. Authentication failures, timeouts and provider errors never switch
  backend.
- 🚨 **Custom LMs change shape.** `BaseLM.forward()` / `aforward()` integrations emit
  `DeprecationWarning` in 3.4 and are **removed in 3.5**. The replacement is an engine object with
  `complete(Request) -> Response`, passed as `dspy.LM(..., engine=...)`. DSPy keeps caching, retries,
  callbacks, history and usage accounting. **If our `LLMClient` is ever wrapped for DSPy, write an
  engine, not a `BaseLM` subclass.**
- `lm(messages=[...])` in the OpenAI style is deprecated (removed in 3.5). `lm("text")` stays.
- The experimental 3.3 types `dspy.LMRequest` and `dspy.LMResponse` are **removed** and replaced by
  `dspy.lm15.Request` and `Response`, which are frozen dataclasses.
- Unknown cost stays unknown, not zero. Rate-limit errors keep `retry_after` and request IDs.
  Asking native execution for `n` answers sends `n` separate requests, so input tokens can be billed
  `n` times.

### Decision types and ReAnchor (experimental)

- `dspy.experimental.Noul`, `Choice[...]` and `Score[...]` are output types that carry
  **probabilities and a confidence** alongside the decision. They work with ordinary generative models
  through `ChatAdapter` and `JSONAdapter`. The docs warn that with a generative model *"confidence
  is self-reported"*.
- `ReAnchor` fits a decision's thresholds, score cuts and choice weights against the program's
  metric. It needs a held-out fold check to accept a change, and it never rewrites instructions.
- **Where this fits here:** the judge's `uphold` / `overturn` / `revise` could be a `Choice`, giving
  a recorded probability for each ruling. That is useful for calibration later. A self-reported
  probability is not evidence, though, so this comes after the readings work, not instead of it
  ([three-roles-goal.md](three-roles-goal.md)).

### Adapters

- `ChatAdapter` now falls back to `JSONAdapter` **only on `AdapterParseError`**. In 3.3.1 it fell
  back on any exception. Engine failures and programming bugs now propagate.
- Non-string `Literal` members are coerced during parsing.

### Optimisers

- `GEPA` gains `code_proposer=`, for proposing `Flex` source code, alongside `instruction_proposer=`.
- `GEPA` **fixes a 3.3.1 bug** in which failed examples could shift or drop out of the scores it
  captures from traces. That bug would corrupt exactly the kind of run described in
  [optimization.md](optimization.md), which is a reason to run GEPA on 3.4, not 3.3.1.
- `BootstrapFewShot` now samples labelled demos independently for each predictor.

### Other

- `LocalInterpreter` runs generated code in plain CPython with host access. It is not a sandbox,
  and nothing here needs it.
- `RLM` breaking change: an interpreter override is now passed as keyword-only `interpreter_factory=`.
  Not used here.
- `ReActV2` gains async support. Not used here.
- Versioned documentation: the docs site now publishes a snapshot per release, and `/current/`
  tracks development.
